# FIXES 2026-05-04 — ограничение polling и равномерное распределение визитов

## Инцидент

В polling-режиме сервис последовательно запускал полный assignment cycle для каждого открытого service point из runtime cache. Из-за этого ограничение `application.assignment.max-visits-per-cycle` фактически применялось не к отделению, а к одному врачу/точке обслуживания. При нескольких активных врачах общий объем переводов мог стать равным `maxVisitsPerCycle * количество_врачей`, а в старой сборке без фактического лимита один врач мог забрать все подходящие визиты.

В приложенном фрагменте `around_1509_business.log` видно, что в 15:09 polling сначала обработал `servicePoint=34020000000001 staff=1 workProfile=116`, выбрал `selectedService=148 targetQueue=405` и перевел визиты `30256..30269`; итог цикла — `processed=14`. Следующий врач `staff=258 workProfile=96` стартовал уже после этого и увидел остаток очереди.

## Исправление

1. `PollingReconciliationJob` больше не вызывает `assignmentService.process(context)` отдельно для каждого врача.
2. Для каждого отделения polling теперь собирает список открытых runtime-врачей и вызывает единый branch-level метод `processPollingBranch`.
3. `processPollingBranch`:
   - берет branch lock один раз на отделение;
   - читает очередь "Врач не назначен" один раз;
   - сортирует визиты согласно `visit-processing-sort-order`;
   - применяет `max-visits-per-cycle` к общему списку визитов отделения до чтения деталей;
   - для каждого выбранного визита подбирает врача из всех доступных кандидатов;
   - балансирует выбор по текущей нагрузке целевых очередей и врачей внутри одного polling batch;
   - активирует операторский контекст непосредственно перед изменением визита выбранным врачом.
4. Добавлен тест `pollingAppliesOneBranchLimitAndBalancesSelectedVisitsAcrossAvailableDoctors`, который фиксирует сценарий: 5 визитов в очереди, лимит 3, 2 врача с разными очередями. Ожидается чтение деталей только трех самых старых визитов и распределение переводов между очередями `901/902/901`.

## Важное замечание по деплою

Логи инцидента не содержат строки `maxVisitsPerCycle=... processingLimit=...`, поэтому они похожи на запуск старой сборки, где новый лимит еще не был развернут. После деплоя исправленной версии в бизнес-логе должна появляться строка вида:

```text
Polling branch assignment source=POLLING branchId=... doctors=... unknownDoctorQueue=... count=... sortOrder=OLDEST_FIRST maxVisitsPerCycle=3 processingLimit=3
```

Если вместо нее по-прежнему видны только строки вида `Visits in unknown-doctor queue ... count=...` без `processingLimit`, значит на стенде запущен старый jar.
