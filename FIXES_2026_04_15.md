## Что изменено по результатам анализа логов `med-doctor-assignment-service160426`

### 1. Ранний mutating workflow от `SERVICE_POINT_OPEN` отключён по умолчанию
- Добавлены флаги:
  - `application.assignment.service-point-open-trigger-enabled=false`
  - `application.assignment.set-work-profile-trigger-enabled=true`
- `DoctorAssignmentEventHandler` теперь пропускает входящие события, если соответствующий trigger отключён конфигурацией.
- В `application.yml` websocket по умолчанию подписывается только на `SET_WORK_PROFILE`.

### 2. Починено выделенное бизнес-логирование
- `logback.xml` переведён с устаревших пакетов `com.qsystems.medrobot...` на реальные пакеты `com.qsystems.meddoctorassignment...`.
- Теперь `med-robot-busines.log` должен содержать:
  - восстановленный контекст врача,
  - старт и завершение assignment cycle,
  - полные логи assign/transfer запросов,
  - предупреждения о неподтверждённых допущениях адаптера.

### 3. Усилена диагностика doctor context и visit workflow
- `DefaultLoggedDoctorContextResolver` теперь пишет в лог итоговый `DoctorContext` со всеми источниками полей.
- `DefaultVisitAssignmentExecutor` пишет расширенные логи начала assign/transfer workflow.
- `ConfigurableVisitWorkflowGateway` пишет:
  - `branchId`, `visitId`, `serviceId`, `staffId`, `servicePointId` для assign,
  - payload перевода визита,
  - тело успешного ответа `200`.

### 4. Зафиксированы неподтверждённые гипотезы интеграции
- Для assign добавлено предупреждение, что текущий адаптер пока **не включает** `staffId/servicePointId` в payload и только логирует этот контекст.
- Для transfer добавлено предупреждение, что `fromId` всё ещё трактуется как `source entry point id` из конфигурации и должен быть подтверждён трассой штатного UI Orchestra.

## Что эти правки должны дать в следующем прогоне
- исчезновение раннего цикла от `SERVICE_POINT_OPEN`;
- появление полноценного `med-robot-busines.log`;
- прозрачную картину: какой контекст врача был восстановлен, какой exact payload ушёл в Orchestra и что вернул сервер на `200/403`.

## Что ещё остаётся неподтверждённым
- точный contract `assign-service-path` для реального перехода с услуги `72 -> 4`;
- точный смысл `fromId` в `transfer-visit-path`;
- наличие обязательного промежуточного шага активации operator/entrypoint context в Orchestra UI.


### 5. Повторное использование mutation-cookie отключено по умолчанию
- Добавлен флаг `application.orchestra.replay-mutation-cookies=false`.
- `OrchestraSessionCookieStore` продолжает **сохранять** cookie от PUT/POST для диагностики, но больше не отправляет их автоматически на следующие mutating-запросы.
- Это сделано по результатам логов, где первый PUT без cookie проходил, а все последующие PUT с mutation-cookie массово получали `403`.

### 6. Цикл теперь аварийно завершается после первого контекстного отказа mutation
- Добавлен флаг `application.assignment.abort-cycle-on-forbidden-mutation=true`.
- `AutonomousMedicalExamAssignmentService` теперь останавливает текущий цикл после первого `403 Forbidden` на mutating REST или после явной контекстной ошибки.
- Это предотвращает серию одинаковых `403` по всем оставшимся визитам в очереди.

### 7. Ответ assign с `userState=INACTIVE` больше не считается успехом
- Добавлен флаг `application.assignment.treat-inactive-user-state-as-failure=true`.
- `ConfigurableVisitWorkflowGateway` анализирует тело ответа успешного assign и, если Orchestra вернула `userState=INACTIVE`, выбрасывает контекстную ошибку вместо перехода к `transfer`.
- Это делает следующий прогон более честным: сервис больше не будет интерпретировать формальный `200` как готовность к безопасному переводу визита.


### 8. `transfer-visit` теперь корректно обрабатывает `204 No Content`
- `ConfigurableVisitWorkflowGateway.transferVisitToQueue(...)` переведён с `retrieve(..., String.class)` на чтение полного `HttpResponse`.
- Ответ Orchestra со статусом `204` и пустым телом теперь считается штатным успешным результатом transfer, а не ошибкой `Empty body`.

### 9. Ответ assign с `userState=NO_STARTED_SERVICE_POINT_SESSION` теперь тоже считается контекстной ошибкой
- Добавлен флаг `application.assignment.treat-no-started-service-point-session-as-failure=true`.
- `ConfigurableVisitWorkflowGateway` теперь распознаёт не только `INACTIVE`, но и `NO_STARTED_SERVICE_POINT_SESSION` как неготовность mutating EntryPoint context.
- Это позволяет останавливать цикл раньше и не интерпретировать формальный `200` как полностью валидный операторский контекст.
